## 1. 프로젝트 한 줄 정의

**모아(MOA)** — 매출과 매장 운영 데이터를 한곳에 모아 현황을 파악하고 분석하는 매장 관리 서비스.
(Manage · Observe · Analyze / "매출을 모아, 인사이트를 더하다.")

### 1.1 과제 메모 → MOA 매핑

토의 메모는 "가계관리(가계부)"를 예시로 설명하고 있다. MOA는 이를 **매장(가게)** 관점으로 치환해 적용한다.

| 메모의 개념 (가계) | MOA 적용 (가게) |
|---|---|
| 수입 | 매출 |
| 지출 | 비용(재료비, 인건비, 임대료, 공과금 등) |
| 예산 | 매장 운영 예산 / 목표 매출 |
| 지출 유형(식비, 공과금…) | 비용·매출 분류 체계(카테고리) |
| 가계 리포트 | 매장 운영 리포트 |

### 1.2 메모에 적힌 핵심 기능 아이디어

- 수입(매출)에 따라 예산을 정리한다.
- 지출(비용) 발생 시 예산에서 차감한다.
- **Daily**로 잔여 예산 리포트를 제공한다.
- **1년 치** 예산을 잡고 운영한다.
- 입력(기입)이 정확해야 하며, 유형(카테고리)을 정할 수 있어야 한다.
- **주간/월간 리포트**를 AI가 생성한다.

## 2. 세 가지 핵심 키워드

메모 전체를 관통하는 키워드는 **AI Native + DDD + TDD** 세 가지다.

```
AI Native  ─ AI가 "내 매장"에 대해 추론·리포트하는 기능을 서비스 안에 내장
DDD        ─ 도메인 주도로 분석·설계 (Domain-Driven Design)
TDD        ─ 테스트 주도로 개발·검증 (Test-Driven Development)
```

| 키워드 | 담당 단계 | 산출 |
|---|---|---|
| DDD | 요구사항정의 · 기획 · 분석 | 도메인 모델, 도메인별 Chapter, 기능별 PRD |
| TDD | 개발 · 검증 | 테스트 케이스(TC), 단위 테스트 코드, 구현 코드 |
| AI Native | 전 단계 | AI 기능 요구사항, 학습 문서 구조, 산출물 검증 |

## 3. 개발 방법론

### 3.1 DDD 기반 분석 (도메인 주도 개발)

메모: *"① 도메인 분석 → 도메인 기반 설계 → 기능별 breakdown, 쪼개기"*

1. **도메인 분석** — 서비스가 다루는 영역(도메인)을 식별한다.
2. **도메인 기반 설계** — 각 도메인의 책임과 경계를 정의한다.
3. **기능별 breakdown** — 도메인 안의 기능을 작은 단위로 쪼갠다.

메모의 예시(쇼핑몰):

```
쇼핑몰
├─ 회원관리  ─ 회원등록 / 삭제 / 수정 …   ← MSA 수준 (기능 단위)
├─ 상품관리
├─ 매출관리
└─ …                                      ← SOA 수준 (시스템 단위)
```

MOA에 적용할 도메인 후보(요구사항정의 단계에서 확정):

```
MOA
├─ 매장(Store)        ─ 매장 정보, 운영 설정
├─ 매출(Sales)        ─ 매출 기입, 조회, 수정, 삭제
├─ 비용(Expense)      ─ 비용 기입, 카테고리, 차감
├─ 예산(Budget)       ─ 연간/월간 예산, 잔여 예산
├─ 분류(Category)     ─ 매출·비용 유형 체계, AI 추론 분류
├─ 리포트(Report)     ─ 일간/주간/월간 리포트, AI 생성 인사이트
└─ AI 학습(Knowledge) ─ 학습 문서, 피드백 반영
```

### 3.2 아키텍처 관점: SOA vs MSA

메모: *"SOA(시스템으로 쪼개기) / MSA(시스템 안에 또 기능을 작게 쪼개기). 중요 차이! 따로 떨어져 있는 시스템에 대해 DB가 같이 있느냐, 분리되어 있느냐."*

| 구분 | SOA | MSA |
|---|---|---|
| 쪼개는 단위 | 시스템(서비스) 단위 | 시스템 안의 기능 단위 |
| DB | 공유 가능 | 서비스별 분리 |
| 메모의 예시 | 쇼핑몰의 회원/상품/매출 시스템 | Daum 검색 플랫폼 |

**MOA의 입장 (2026-10-18 확정)**

규모를 먼저 짚는다. 쇼핑몰 전체가 여러 서비스(회원/상품/주문/결제)로 이뤄진 시스템이라면, MOA는 그중 **서비스 하나 정도의 크기**다. 따라서 MOA를 6개 서비스로 쪼개는 것은 과하고, 서비스 하나 안의 **모듈** 단위로 경계를 나눈다.

| 선택지 | 구조 | 판단 |
|---|---|---|
| A. 모듈러 모놀리스 | DB 1개, 패키지 경계만 | MSA 체감 없음 |
| **B. 스키마 분리** | DB 서버 1개, 모듈별 스키마(MySQL에서는 데이터베이스) | **채택.** 데이터 소유권 체감, 모듈 간 JOIN 차단, 설정 부담 적음 |
| C. 일부 물리 분리 | 본체 + 별도 서비스, DB 분리 | Phase 2 AI 서비스에만 적용 |

- **Phase 1 = MOA Core 서비스 하나.** 매장·매출·비용·분류·예산·리포트(집계)를 모듈로 나누고, MySQL 서버 하나 안에 **모듈별 데이터베이스(스키마)** 를 둔다. 모듈 간 FK·JOIN 금지, 호출은 공개 API와 도메인 이벤트로만 한다. Spring Modulith가 이를 테스트로 강제한다.
- **Phase 2 = AI 서비스를 물리적으로 분리.** 런타임이 다르고(Ollama 별도 프로세스), 응답 시간이 길며(초 단위), 장애가 나도 매출 입력은 돌아가야 하므로 MOA에서 유일하게 서비스 분리 가치가 있는 영역이다. Core의 도메인 이벤트를 구독해 동작하며 Core 코드는 수정하지 않는다.

```
[MOA Core 서비스]  store · sales · expense · category · budget · report   ← 모듈러 모놀리스, MySQL 서버 1개 / 스키마 6개
        │  도메인 이벤트 / HTTP
        ▼
[MOA AI 서비스]    분류 추론 · 리포트 서술 · 학습 자료 관리                ← Phase 2, 별도 프로세스 · 별도 DB
```

쇼핑몰 비유로는 "회원관리 / 재고관리"가 아니라 **"주문 서비스 / 결제 서비스"** 의 관계에 가깝다.

### 3.3 TDD 기반 개발 (테스트 주도 개발)

메모: *"기능마다 단위 테스트를 붙여서 기능이 다 잘 동작하게 해야 한다."*

- 모든 기능은 **단위 테스트를 먼저** 작성하고 구현한다. (Red → Green → Refactor)
- 기능별 PRD에 **TDD 항목(테스트 케이스)을 반드시 포함**한다.
- PRD → TC 생성 → 단위 테스트 코드 → 구현의 순서를 지킨다.
- 테스트는 "구현된 기능을 검증하는 용도"로, 요구사항정의서 작성 시점부터 함께 고려한다.

## 4. AI Native 방향

### 4.1 AI Native의 정의 (메모 기준)

> *"산출물을 잘 검증했는가 여부. 여기서 AI를 잘 활용했느냐." (by Jay)*

AI Native는 두 가지 층위를 모두 뜻한다.

1. **개발 과정의 AI Native** — 요구사항, PRD, TC, 코드 등 모든 산출물을 AI로 생성하고, **AI로 검증**한다. 검증이 잘 되었는지가 평가 기준이다.
2. **서비스의 AI Native** — *"AI가 내 매장에 대해 추론할 수 있는 기능을 도입해야 함."* 서비스 자체에 AI 추론 기능을 내장한다.

### 4.2 서비스에 내장할 AI 기능

| 기능 | 메모 근거 | 설명 |
|---|---|---|
| 주간/월간 리포트 생성 | *"주간/월간 리포트 → 자산관리 정책(ex. 분류) 등을 기반으로 AI가 생성"* | 비즈니스 조직 관점이 아니라, 사용자가 정한 **운영 정책(분류 체계 등)** 을 근거로 AI가 리포트를 작성 |
| 유형(카테고리) 추론 | *"유형을 정할 수 있어야 함 (ex) 식비, 공과금… ⇒ AI 추론"* | 매출·비용 입력 시 AI가 카테고리를 추론해 제안 |
| 정확한 기입 보조 | *"기입이 정확해야 함 (ex) 지출 Input"* | 입력 데이터의 정확성이 AI 추론의 전제. 입력 검증·보정 |
| 일간 잔여 예산 리포트 | *"Daily로 잔여 예산 리포트"* | 예산 대비 현황을 매일 제공 |

### 4.3 AI 학습 자료 구조

메모: *"기학습자료 + 추가학습자료 → 학습을 위한 자료 구조를 만들고 업데이트 해줘야 함"*

- **기학습 자료**: 기본 분류 체계, 매장 운영 상식 등 초기 지식.
- **추가학습 자료**: 사용 과정에서 쌓이는 매장별 지식.
  - 예: `교통비` → `여행 교통비`, `출장 교통비`처럼 사용자 맥락에 맞게 세분화된다.
- **피드백 루프**: *"주간 리포트를 확인하여 → 결제(승인) 후 AI에게 학습"*
  - 사용자가 리포트/분류 결과를 **검토·승인(결제)** 하면, 그 결과가 추가학습 자료에 반영된다.
- **포맷**: *"Markdown 기반으로 학습 문서 생성이 제일 좋음"* — 학습 자료는 Markdown으로 관리한다.

```
knowledge/
├─ base/        ─ 기학습 자료 (기본 분류 체계, 정책)
└─ learned/     ─ 추가학습 자료 (승인된 리포트, 세분화된 분류)
```

### 4.4 검색·조회 전략: RAG → Graph RAG / 온톨로지

메모: *"AI가 추가학습 자료에서 검색·조회하는 것 → RAG. ∴ 문서가 커지고 복잡해지면 → 비용↑"*

| 단계 | 방식 | 설명 |
|---|---|---|
| 1단계 (시작) | **RAG** | Markdown 학습 문서를 검색해 컨텍스트로 제공 |
| 2단계 (개선 ①) | **Graph RAG** | 온톨로지 구조를 학습시킨 그래프 기반 검색 |
| 2단계 (개선 ②) | **온톨로지** | hierarchy 구조화 → tree 생성 → 요소 간 관계 연결 → 관계 그래프(지식 그래프) 생성 |

- 문서가 커지면 RAG 비용이 증가하므로, 분류 체계를 처음부터 **계층(tree) 구조**로 설계해 온톨로지/Graph RAG로의 전환을 쉽게 한다.
- 4.3의 `교통비 → 여행 교통비 / 출장 교통비` 세분화가 곧 온톨로지의 hierarchy다.

**현실적 구현 경로 (2026-10-17 검토)**

| 단계 | 구현 방식 | 판단 |
|---|---|---|
| RAG | 학습 자료가 Markdown 수십 개 수준이면 벡터 DB 없이 관련 문서를 프롬프트에 직접 넣는 **in-context RAG**로 시작. 문서가 커지면 임베딩 + 로컬 벡터 검색(SQLite-vec, Chroma 등)으로 전환 | 1차 구현 |
| 온톨로지 | 카테고리 hierarchy를 **YAML/Markdown tree**로 정의(`비용 > 교통비 > 출장 교통비`). 코드에서 tree를 탐색해 관련 노드와 상위/하위/형제 관계만 추려 LLM에 전달. 그래프 DB 불필요 | 1차 구현 |
| Graph RAG | Microsoft GraphRAG, Neo4j 등은 토이프로젝트 데이터량 대비 과함. 온톨로지 tree에 노드 간 관계 엣지를 추가하는 **경량 지식 그래프**로 핵심 아이디어만 가져옴 | 2차 확장 |

- 결론: **in-context RAG → YAML 온톨로지 tree → (여유 시) 관계 엣지 추가** 순으로 진행한다. Graph RAG 본격 도입은 범위에서 제외한다.

### 4.5 Local LLM

메모: *"LLM 비용 절약 / 폐쇄망 사용 및 특정 활용 / PC에 설치해서 사용해보기"*

- 목적: 비용 절감, 폐쇄망 환경 대응, 특정 용도 활용.
- 실행 자원 이해:

| 자원 | 역할 | 메모 예시 |
|---|---|---|
| CPU | 결과 생성(추론 실행) | HP, AMD |
| Memory | 토큰 수신, 파라미터 메모리 적재 | 삼성, 하이닉스 |
| GPU | 답변 생성을 위한 연산 | 엔비디아 |

- MOA에서는 **클라우드 LLM을 기본**으로 하되, 분류 추론 등 단순 작업은 Local LLM으로 대체 가능하도록 **LLM 호출부를 추상화**한다.

**개발 환경 확인 (2026-10-17)**

| 항목 | 확인 결과 | 의미 |
|---|---|---|
| 칩 | Apple M1 Pro | Metal 가속으로 Ollama 구동 가능 |
| 메모리 | 16 GB (통합 메모리) | GPU 전용 VRAM 없음. 메모리 용량이 모델 크기 상한. **7B~8B(4bit 양자화)** 가 쾌적, 14B까지 구동 가능 |
| Ollama | 미설치 | Phase 2에서 설치 |
| 런타임 | Node v22, Python 3.9(시스템 기본) | Python 스택 선택 시 3.11+ 별도 설치 필요 |

**현실적 구현 방안**

- 실행 환경: **Ollama**. OpenAI 호환 API를 제공하므로 `LLMClient` 인터페이스 하나에 클라우드(Claude) 구현체 / Ollama 구현체를 두고 설정값으로 교체한다.
- 모델 후보: Qwen 2.5/3 7B, Llama 3.1 8B, EXAONE 3.5 7.8B(한국어 특화), Gemma 3.
- 역할 분담:

| 작업 | LLM | 이유 |
|---|---|---|
| 카테고리 추론(분류) | Local LLM | 짧은 입출력, 빈번한 호출 → 비용 절감 효과 큼. 7B로 충분 |
| 주간/월간 리포트 생성 | 클라우드(Claude) | 긴 한국어 생성 품질과 추론 깊이 필요 |
| 피드백 → 학습 문서 갱신 | 클라우드(Claude) | 구조화된 Markdown 생성의 정확도 |

- 주의: Local LLM의 한국어 장문 생성 품질은 클라우드 대비 확실히 낮다. **카테고리 추론 용도로 한정**한다.

## 5. 진행 프로세스

메모: *"요구사항정의서 만들 때부터 DDD/TDD → 그래야 도메인별로 Chapter 만들어줌 → 기능별로 PRD 생성(TDD를 꼭 포함) 후 하나씩 점검 → 개발 진행 → TC 생성 가능 → Unit 테스트 코드 → TDD"*

```
[1] 요구사항정의
     │  DDD 관점으로 작성. 도메인 식별, TDD 검증 기준 포함
     ▼
[2] 기획
     │  도메인별 Chapter 구성, 기능별 breakdown
     ▼
[3] 분석
     │  기능별 PRD 생성 (TDD 항목 필수 포함) → 하나씩 점검
     ▼
[4] 개발
     │  PRD 1건 → TC 생성 → 단위 테스트 코드 → 구현 (TDD)
     ▼
[5] 검증
        단위 테스트 통과 확인, AI를 활용한 산출물 검증
```

- 각 단계의 산출물은 다음 단계의 **입력**이 된다.
- [3]~[5]는 PRD 단위로 **반복**한다. (한 PRD를 끝까지 돌린 뒤 다음 PRD로)

### 5.1 Phase 구분: 서비스 구현 → AI 탑재

"한 번에 다 만들지 않는다"는 원칙에 따라 프로젝트를 두 Phase로 나눈다. 다만 **Phase 1은 AI를 모르는 채로 만들지 않는다** — AI 기능 자체는 붙이지 않되, 붙일 자리를 설계 단계에서 확보한다.

| Phase | 범위 | 핵심 도메인 | AI 관련 |
|---|---|---|---|
| **Phase 1 서비스 구현** | 매출·비용 기입, 예산, 분류, 기본 리포트(집계) | 매장 / 매출 / 비용 / 예산 / 분류 / 리포트 | 기능 없음. 단, 아래 "Phase 1에서 미리 설계할 것" 반영. 개발 과정에서는 AI로 산출물 생성·검증 (4.1 ①) |
| **Phase 2 AI 탑재** | 카테고리 추론, AI 리포트 생성, 피드백 → 학습 문서 갱신, Local LLM | AI 학습(Knowledge) | RAG → 온톨로지(4.4), Ollama + 클라우드 LLM 추상화(4.5) |

**Phase 1에서 미리 설계할 것** (나중에 AI를 붙일 때 구조를 뒤집지 않기 위한 최소 장치)

1. **분류 체계를 tree로** — 카테고리를 flat 목록이 아니라 계층 구조(부모-자식)로 모델링한다. Phase 2 온톨로지의 뼈대가 된다.
2. **`LLMClient` 포트(인터페이스)만 정의** — 구현체는 두지 않는다. 분류 서비스·리포트 서비스가 이 포트에 의존하도록 경계만 잡아둔다. Phase 1에서는 "사용자가 직접 분류"가 유일한 구현이다.
3. **AI가 추론에 쓸 데이터를 처음부터 저장** — 매출·비용 기입에 자유 텍스트 메모(설명) 필드, 분류 결과에 "누가 정했는가(사용자/AI)"와 "승인 여부" 필드를 둔다. Phase 2의 분류 추론·피드백 루프의 입력이 된다.
4. **리포트를 데이터와 서술로 분리** — Phase 1 리포트는 집계 숫자(데이터)만 생성한다. Phase 2에서 그 데이터를 LLM에 넣어 서술(인사이트)을 덧붙이는 구조가 되도록 리포트 도메인을 "집계 → 서술" 2단으로 설계한다.
5. **기학습 자료(`knowledge/base/`)의 초안은 Phase 1 분류 체계 확정 시 함께 작성** — 카테고리 tree를 Markdown으로 내보내면 그것이 곧 기학습 자료다.

**이렇게 나누는 이유**

- Phase 1 단독으로도 "매출을 모아 현황을 파악하는" 완결된 서비스가 된다. (Manage · Observe)
- Phase 2는 그 위에 Analyze를 더하는 것이므로, Phase 1의 데이터 모델이 안정된 뒤에 붙이는 것이 맞다.
- AI를 처음부터 섞으면 LLM 응답 불확실성이 TDD 사이클을 흔든다. Phase 1에서 결정적(deterministic) 로직을 테스트로 고정한 뒤, Phase 2에서 LLM 호출부를 mock으로 격리해 테스트하는 순서가 안전하다.

## 6. 작업 원칙

1. **한 번에 다 만들지 않는다.** *"한번에 다 만들지 X → PRD 하나씩 차근차근"* — PRD 1건 단위로 개발·검증을 완료하고 다음으로 넘어간다.
2. **요구사항정의서부터 DDD/TDD를 적용한다.** 나중에 끼워 넣지 않는다.
3. **모든 PRD에는 TDD 항목이 포함된다.** TC 없는 PRD는 완성이 아니다.
4. **모든 기능에는 단위 테스트가 붙는다.** 테스트가 기능 동작의 증거다.
5. **도메인 경계를 지킨다.** 도메인 간 직접 의존을 피하고, DB 소유권을 도메인별로 나눈다.
6. **AI 산출물은 반드시 검증한다.** AI가 만든 문서·코드·테스트는 AI와 사람이 함께 검토한다.
7. **학습 자료는 Markdown으로 관리한다.** AI 학습 문서, 프로젝트 문서 모두 Markdown.
8. **브랜드 방향을 따른다.** 직관적·간결함·신뢰·데이터 기반. 불필요한 요소를 줄인 대시보드.
9. **문서는 자기완결적으로, 수는 적게.** 다른 문서를 참조하지 않고 그 문서만 읽어도 이해되게 쓴다. 새 단계가 생기면 새 문서보다 기존 문서의 장으로 넣는다.
10. **기획 중 기능 추가 기준 (2026-10-20).** 기획서를 쓰다가 새 기능이 떠오르면 둘로 나눈다. **데이터 구조가 바뀌는 것**(예: 휴무 여부, 결제수단 삭제)은 지금 넣는다. 나중에 넣으면 설계를 다시 해야 한다. **화면 편의만 더하는 것**(예: 말풍선, 패널 안 날짜 이동)은 "선택"으로 넣거나 Phase 2 후보로 적어 둔다. 사용자가 추가를 제안하면 AI는 이 기준으로 판단해 근거와 함께 "지금 / 선택 / Phase 2"를 먼저 제안하고, 결정은 사용자가 한다.

### 6.1 검토 단위 (2026-10-19)

Phase 1 전체를 한 번에 검토할 수 없으므로 **모듈 → 기능 → 검토 지점** 세 층으로 나눈다.

**모듈 사이클.** 모듈(= 화면) 하나가 한 사이클이고, 사이클마다 사용자가 보는 지점이 네 번 있다.

| 지점 | 보는 것 | 분량 | 사용자 역할 |
|---|---|---|---|
| ① PRD 초안 | 화면 구성, 입력 규칙, 검증 기준 | 100~150줄 | 기획자로서 확정 |
| ② 설계 요약 | 애그리거트 표, 이벤트 목록, 공개 API 표 | 30~50줄 | PRD와 맞는지 확인 |
| ③ 구현 | 기능 하나씩, 아래 보고 형식 | 기능당 10분 | 검증자 |
| ④ 동작 확인 | 실제로 눌러 보기 (백엔드만 있을 때는 Swagger, 프론트 이후는 화면) | 10~20분 | 사용자 |

**기능 단위 보고.** 모듈 안에서 기능 하나씩 구현하고, 기능마다 다음을 보고한 뒤 확인을 받고 다음 기능으로 넘어간다. git 커밋 하나 = 기능 하나.

- 구현한 기능 이름
- PRD 검증 기준 각 항목 ↔ 테스트 이름 대응표 (빠진 항목이 없는지가 핵심)
- 테스트 실행 결과 (통과 개수, 실패 내용)
- 봐야 할 파일 1~2개와 이유

**코드에서 실제로 읽는 범위.** 코드 전체를 검토하는 것이 아니라 "요구사항이 테스트로 빠짐없이 옮겨졌고 통과했다"를 검토한다.

| 읽는다 | 읽지 않는다 |
|---|---|
| 테스트 이름 목록 (PRD 검증 기준과 대조) | 테스트 본문 |
| 애그리거트 클래스 (규칙이 코드로 맞게 들어갔나) | 리포지토리, 컨트롤러, 설정 파일 |
| 공개 API 메서드 시그니처 | 내부 구현 |
| 테스트 실행 결과 | 빌드 로그 |

**2주차(store·category)는 읽는 범위를 넓힌다 (2026-10-25, Muse 리뷰).** 11/05 체크포인트가 "JPA를 계속 쓸 것인가"이므로, JPA가 실패하는 지점을 직접 본다. 위 표에 더해 ① 리포지토리 메서드 목록(메서드 이름 쿼리가 의도대로 읽히는가), ② 엔티티의 매핑 어노테이션, ③ `@Transactional`이 붙은 메서드, ④ Flyway V1 SQL 전문을 읽는다. 3주차부터는 원래 표로 돌아간다.

기능별 검토 결과(확인 / 수정 요청 / 보류)는 `05_verification.md`에 한 줄씩 쌓는다. 이것이 AI 산출물 검증 기록이다.

**흡수를 위한 세 가지 (2026-10-24 추가).** 완성 코드를 읽기만 하면 "이해한 느낌"만 남으므로, AI가 짜는 1·2·4주차에는 아래를 함께 한다.

1. **TDD 순서 그대로 보여 준다.** 기능 하나를 완성본이 아니라 "테스트 이름 → 실패 → 최소 코드 → 통과 → 정리" 커밋 단위로 쪼개서 전달한다. 읽는 순서는 테스트 → 애그리거트 → 응용 서비스. 나머지는 읽지 않아도 된다.
2. **기능마다 질문 두 개.** AI가 "이 규칙은 어느 파일 어느 메서드에 있고 왜 거기인가" 같은 질문 두 개를 내고, 사용자가 답을 쓴 뒤 다음 기능으로 간다. 답을 못 쓰는 자리가 안 붙은 곳이므로 그 부분만 다시 설명한다. 질문과 답은 `05_verification.md`에 남긴다.
3. **모듈마다 한 조각은 사용자가 따라 쓴다.** AI가 짠 패턴을 보고 같은 모양의 작은 기능 하나(메서드 하나 + 테스트 하나, 30분 분량)를 직접 추가한다. 예: store의 `update()`, category의 "상위가 꺼져 있으면 하위를 켤 수 없다". 3주차 직접 구현의 준비 운동이다.

**3주차 sales 모듈은 역할을 뒤집는다 (2026-10-24 결정).** 사용자가 설계 문서를 보고 직접 구현하고, AI가 리뷰한다. 읽고 검증하는 능력은 1·2주차에서 늘지만 빈 파일에서 짜는 손은 직접 써야만 붙기 때문이다. 시간이 2~3배 걸리는 것은 6주차 버퍼로 흡수한다. 설계 요약(②)도 사용자가 먼저 쓰고 AI가 리뷰한다 (2026-10-27 결정). 막히면 category의 애그리거트 밖 규칙 표(04 2.3)를 힌트로 본다.

진행 순서는 02 → 03 → 04 → 개발 → 05 이다 (2026-10-19 변경. 이전에는 도메인 설계를 PRD 앞에 뒀으나, 02에서 모듈 경계와 용어가 이미 고정되었으므로 관례대로 기획(PRD)을 설계보다 앞에 둔다). 제품 구체화와 요구사항을 한 문서(02)에 둔 이유는 시나리오가 곧 이벤트 스토밍의 재료라서 나눠 두면 왔다 갔다 읽어야 하기 때문이다.

**03 기획은 페이지 7개를 먼저 한꺼번에 쓰고, 04 설계·구현은 모듈 단위로 반복한다** (2026-10-19 결정). 대시보드·리포트 페이지는 매출·비용·예산 페이지의 결정에 의존하고, 설계는 모듈 전체 그림이 있어야 애그리거트 경계를 바르게 자를 수 있기 때문이다. 기획이 끝나면 store 설계·구현 → category 설계·구현 → … 순서이고, `04_design.md`는 모듈이 하나 구현될 때마다 그 장이 채워진다.

**세 문서가 서로 다른 질문에 답한다** — 요구사항·PRD·설계가 비슷해지지 않도록 지키는 경계

| 문서 | 답하는 질문 | 관점 | 다루는 것 | 다루지 않는 것 |
|---|---|---|---|---|
| 02 요구사항 | 무엇이 있어야 하고, 됐다고 어떻게 아는가 | 사용자·사업 | 시나리오, 기능 목록, 결과 수준의 수용 조건 (Given/When/Then 한 줄) | 화면 상세, 내부 구조 |
| 03 PRD | 사용자에게 어떻게 보이고 어떻게 동작하는가 | 기획자 | 화면 구성과 흐름, 입력 항목·형식·기본값·필수 여부, 상태별 표시, 예외와 안내 문구, 조작 단위의 TC | API, 테이블, 클래스, 이벤트 |
| 04 설계 | 안에서 어떻게 만드는가 | 개발자 | 애그리거트, 값 객체, 도메인 이벤트, 공개 API, 스키마, 모듈 의존, 패키지 | 화면, 문구, 사용자 흐름 |

연결은 **모듈 이름 + 기능 이름**으로 한다. PRD의 제목은 02의 기능 이름이고, 설계의 항목과 단위 테스트 이름(`@DisplayName`)도 같은 기능 이름을 쓴다. FR-001 같은 번호는 두지 않는다 (2026-10-19 결정. 토이 규모에서는 번호 관리 부담이 추적성 이득보다 크다. 기능 이름이 바뀌면 세 문서를 검색해 같이 바꾼다).

**문서 작성 규칙**

- 각 문서는 **자기완결적**으로 쓴다. 읽는 데 필요한 배경은 그 문서 안에 짧게 다시 적고, "다른 문서 N장 참고" 식의 참조는 쓰지 않는다.
- 문서 수는 늘리지 않는다. 단계가 하나 추가되면 새 문서가 아니라 기존 문서의 장으로 넣는 것을 먼저 검토한다.

**저장소 구조**

```
MOA/
├─ README.md     저장소 소개 (처음 보는 사람용)
├─ docs/         프로젝트 문서 (00~05 번호 순, muse-feedback.md)
├─ core/         Spring Boot — MOA Core 서비스 (Phase 1)
│   └─ src/main/java/moa/
│       ├─ store/      ┐
│       ├─ sales/      │ 모듈 = MySQL 데이터베이스(스키마) 1개
│       ├─ expense/    │ 모듈 루트 = 공개 API·이벤트
│       ├─ category/   │ internal/ = 애그리거트·리포지토리·컨트롤러
│       ├─ budget/     │
│       └─ report/     ┘
├─ ai/           AI 서비스 (Phase 2, 별도 프로세스·DB)
├─ frontend/     React + Vite
└─ knowledge/    AI 학습 자료 (Phase 2)
```

- Core는 **모듈 우선 패키지 구조**(package-by-module)를 따른다. 모듈 루트에는 공개 API(application 서비스)와 공개 이벤트만 두고, 애그리거트·리포지토리·컨트롤러는 `internal/` 아래에 둔다.
- 모듈 간 호출은 공개 API 또는 도메인 이벤트로만 한다. 다른 모듈의 `internal/`을 import하거나, 다른 모듈 스키마의 테이블을 FK·JOIN으로 참조하면 Spring Modulith 테스트가 실패한다.
- 모듈 간 참조는 ID로만 한다. 예: `expense`는 `categoryId`만 보관하고 분류 이름이 필요하면 `category` 공개 API로 조회한다.
- `Money`, `YearMonth` 같은 값 객체는 공통 커널(`moa/shared/`)에 두고 모든 모듈이 공유한다.

**DB 스펙 (2026-10-18 확정)**

| 항목 | 결정 | 이유 |
|---|---|---|
| 금액 타입 | `DECIMAL(15,0)` | 원화는 소수점 없음. DOUBLE 금지 |
| 문자셋 | `utf8mb4` | 한글 메모, 이모지 |
| 타임존 | 서버 `Asia/Seoul`, 매출·비용 발생일은 `DATE` | "오늘 매출"이 자정 기준으로 어긋나지 않게 |
| PK | `BIGINT AUTO_INCREMENT` | 토이 규모면 충분 |
| 모듈 간 참조 | ID 컬럼만, FK 제약 없음 | 모듈 경계 유지. 존재 확인은 공개 API로 |

**JPA 최소 사용 규칙** — 사용자가 JPA를 처음 쓰므로 범위를 이 안으로 제한한다. 코드 생성은 AI가 하고 사용자는 검증하므로, 필요한 것은 "읽고 판단하는" 수준이다.

- 사용: `@Entity`, `@Id`, `@Enumerated(STRING)`, `@Embeddable`/`@Embedded`(Money), Spring Data 메서드 이름 쿼리, `@Transactional`
- 모듈 내부 연관관계만 허용: 분류 tree(자기 참조), 예산 항목(`@OneToMany`). 그 외 연관관계 어노테이션 금지
- 모듈 간 참조는 `Long categoryId`처럼 ID 필드. `@ManyToOne`으로 다른 모듈 엔티티를 참조하지 않는다
- 양방향 매핑, cascade, 지연 로딩 튜닝은 Phase 1에서 다루지 않는다
