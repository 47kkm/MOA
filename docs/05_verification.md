# 05 검증 기록

MOA는 AI(Claude Code)가 대부분의 문서와 코드를 쓰고, 사용자(kei)가 검증한다. 이 문서는 그 검증 기록이다.

- **무엇을 남기나**
  - 기능마다 검토 결과 한 줄
  - 기능마다 낸 질문 2개와 사용자의 첫 답. 틀린 답과 정정도 그대로 남긴다
  - 사람이나 리뷰가 AI 산출물에서 잡은 오류
  - 체크포인트 결과
- **어떻게 늘어나나:** 주차마다 장이 하나씩 붙는다. 6주차에는 수용 조건·TC 대비 결과를 더한다.
- **결과 표시**

  | 표시 | 뜻 |
  |---|---|
  | 확인 | 테스트 이름이 검증 기준을 빠짐없이 옮겼고 통과함 |
  | 수정 요청 → 반영 | 검토에서 고칠 점이 나와 고침 |
  | 보류 | 이번 범위가 아님 (선택 기능 등) |
  | 리뷰 대기 | 테스트는 통과. kei 코드 리뷰 전 |

- **질문 답 표시:** ✓ 맞음 · △ 일부 맞음 · ✗ 틀림

### 2.2 질문과 답

2주차는 JPA 체크포인트 때문에 엔티티 매핑·리포지토리·`@Transactional`·SQL까지 읽었다. kei는 PR마다 "## 체크" 리뷰로 고친 답을 남겼다.

| PR | 질문 | 첫 답 | 정정 |
|---|---|---|---|
| #1 | 예외가 발행하는 쪽으로 퍼지지 않는다는 건 어느 테스트, 어떤 코드로 확인? | ✓ `exceptionNotPropagated`, `doesNotThrowAnyException` | |
| #1 | 기본 DB를 "없음"에서 moa로 바꾼 이유? | ✓ Modulith 발행 기록 SQL에 DB 이름이 없고, MySQL에서는 지정 설정도 막힘 | |
| #2 | `Store`에 memo 필드만 더하고 V2 SQL은 그대로 두면? | ✗ "DB에 저장만 안 됨" | `ddl-auto: validate`라 앱 시작 실패. 테이블에만 있는 칸(`created_at`)은 괜찮음 |
| #2 | `update`에 save가 없는데 왜 DB가 바뀌나? `@Transactional`을 지우면? | △ DB 그대로는 맞힘 | 변경 감지는 "바뀔 때"가 아니라 커밋 직전 스냅샷 비교. 응답은 200 + 바뀐 이름이라 성공처럼 보이는 버그 |
| #3 | (연습) 리포지토리 메서드가 어떤 SQL이 되나 | △ WHERE는 거의 맞힘 | 필드 이름이 아니라 칸 이름·스키마, `delete`에 WHERE 있음, `exists`는 `select id … limit 1`. 실제 SQL을 뽑아 비교함 |
| #3 | `@Column` 없는 `sortOrder`는 어느 칸? 칸 이름만 바꾸면? | ✓ `sort_order`(Spring Boot 이름 규칙), 앱 시작 실패 | PR #2의 ✗를 다시 물어 맞힘 |
| #3 | "켜진 상위 최소 1개"는 어디서, 왜 `Category` 밖에서 검사? | △ 위치는 `deactivate`의 for 문이라 답함 / 이유 ✓ | 위치는 `rejectIfLastActiveTop` (끄기·삭제가 같이 부름). 다른 분류를 DB에서 세야 해서 밖 규칙 |
